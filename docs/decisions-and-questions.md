# Salary Management for ACME HR: Decisions

Author: Vineet Kumar | Date: 24 Sep 2026 | Version: 1.1

This document records the decisions for the application, with reasons and alternatives. The clarification questions were shared with the Incubyte team, who replied that everything in the brief is important and left the details to me. I then answered the questions myself; the answers are in `clarification-questions.md`, and the decisions below follow them. The details decided on top of the answers (D24 to D36) were reviewed and confirmed on 24 Sep 2026.

## 1. Engineering decisions

| # | Area | Decision | Reason | Alternatives considered |
|---|---|---|---|---|
| D1 | Language | TypeScript for the API, the UI and shared code | Matches the role. One set of types and validation rules shared by API and UI. | JavaScript |
| D2 | Backend | Node.js 24 LTS with Express 5, Zod for request validation | Matches the role. Express 5 passes errors from async handlers to the error middleware, and Zod schemas can be shared with the UI. | Fastify (built-in schema validation), NestJS (more structure than this size needs) |

| D4 | Data access | Drizzle ORM with versioned migrations | Typed queries that stay close to SQL, which keeps statistics queries readable. | Prisma, Knex |
| D5 | Frontend | React with Vite and TypeScript, as a single page application | An internal tool behind a login does not need server rendering or SEO. A separate API keeps the backend and UI clearly split, as the brief asks. | Next.js |

| D8 | Money | Whole minor units (for example paise or cents) with an ISO 4217 currency code | Avoids floating point rounding errors in totals and averages. | Decimal type in the database |
| D9 | Scale | Paging, filtering, sorting and statistics run in the database, with indexes on the filter columns | About 10,000 employees and around 100,000 pay rows are small for PostgreSQL. The aim is to avoid sending all rows to the browser. | Loading all rows in the UI |

Business rules kept in plain functions so most tests need no database. | Jest, Testcontainers |
| D11 | Seed data | TypeScript seed script using Faker with a fixed seed, inserting in batches | The same 10,000 synthetic employees on every run, so demos and tests are repeatable. No real personal data. | Static CSV file |
| D12 | Quality checks | GitHub Actions runs lint, type check and tests on every push | Keeps the main branch working and shows the checks in the history. | Local checks only |
| D13 | Hosting | Neon for PostgreSQL, Render for the API, Vercel for the UI, Brevo for email, all on free plans | Free tiers and deploys from Git. | One container on Render or Fly.io |
| D14 | Working with AI | Claude Code as a pair programmer. Project rules in `CLAUDE.md` and a short project history in `docs/ai/log.md`. Every AI change is reviewed and covered by tests before it is committed. | Makes AI use visible and keeps quality under my control. | Unrecorded AI use |
| D15 | Commits | Small commits in Conventional Commits style, with tests committed alongside or before the code they cover | Shows how the solution evolved, as the brief asks. | Large feature commits |
| D16 | Scope | Pay data and insights only, no payroll processing (Q10). Features live in separate modules so new ones can be added later. | Matches the answer to Q10 and the problem statement. | Building payroll features |
| D17 | Authentication | Email and password login. A signed JWT (using `jose`) in an httpOnly, Secure, SameSite cookie, with a token version check. Passwords hashed with Argon2id. Login is rate limited. | The token is not readable from JavaScript, which limits the damage of a cross-site scripting bug. | Token in localStorage (readable by scripts), server sessions |
| D18 | Password reset and invites | One token mechanism with two purposes: reset (valid 30 minutes) and invite (valid 72 hours). Random single-use tokens, stored only as a hash, sent as links through the Brevo transactional API. The forgot password response is the same whether or not the email exists. | One well-tested flow serves both cases and does not reveal which emails have accounts. | Admin-set passwords, other email providers such as Resend or SendGrid |
| D19 | Same-origin API | The UI calls the API under `/api` on its own domain: a Vercel rewrite in production and the Vite proxy locally. | Keeps the auth cookie first-party, since browsers increasingly block third-party cookies, and avoids CORS setup. | CORS with cross-site cookies |
| D20 | Import | ExcelJS for .xlsx and csv-parse for CSV. Each row is validated with the same Zod schemas as the API. HR sees a preview with row-level errors, and the file is saved in one transaction only when every row is valid. Employees are matched by employee code. Country HR users can only import rows for their own country. | All-or-nothing import avoids half-loaded data. Reusing the API schemas keeps the rules in one place. | SheetJS (the npm registry copy is outdated), saving valid rows and skipping the rest |
| D21 | Export and file format | An Excel file has two sheets, Employees and Pay components. A CSV file holds one of the two. Export uses the same columns as import and follows the current filters and the user's country scope. | A file exported from the application can be edited and imported back. | One wide sheet with a column per component (breaks when components differ by country) |
| D22 | No server-side cache | Caching only in the browser (TanStack Query), on the CDN and with HTTP headers for reference data. | Data fits in PostgreSQL memory, and a server cache risks showing old pay figures after an edit. | Redis; materialized views as the first step if measurements show a need |
| D37 | Step 00 branch | Step 00 was committed directly on `main`. Every later step uses a `step/NN-short-name` branch from `main`, merged through a pull request. | `main` did not exist yet, so there was no branch to start from or merge into. | An empty first commit on `main`, then a step 00 branch and pull request |
| D38 | TypeScript version | TypeScript 6.0 (`~6.0.3`), with all tooling installed once at the repository root and each workspace checked with its own `tsconfig.json` that extends a strict base. | typescript-eslint, which provides type-aware lint rules, supports TypeScript below 6.1 only; TypeScript 7.0 would break linting. Move to TypeScript 7 once typescript-eslint supports it. | TypeScript 7.0 without type-aware lint rules |
| D39 | Running TypeScript | Node.js 24 runs the API's TypeScript source directly, in development (`node --watch`) and in production. The shared package exports its source, read directly by Node, Vite and Vitest. Imports use `.ts` extensions, and `erasableSyntaxOnly` allows only syntax Node can strip (no enums or parameter properties). Environment files are loaded with `--env-file-if-exists`. | No build step, bundler or extra runner for the API or the shared package, and one way to run the code everywhere. | tsx in development and a tsc or bundler build for production; dotenv |
| D40 | Hosting region and deploy settings | The Render API runs in Ohio and the Neon database in AWS us-east-2 (Ohio), so every database query stays inside one region. Render deploys from `main` only after CI passes. Vercel builds the web app from the repository root with `vercel.json` and rewrites `/api/*` to Render. | The Neon project already existed in us-east-2 and its region cannot be changed, and Render has a matching region. Keeping the API next to the database matters more than the distance to users, since one page can make several queries. | Singapore, closer to India, which would have needed a new Neon project |
| D41 | Running migrations in production | Render's build command runs `npm ci --omit=dev` and then `db:migrate`, using the Drizzle migrator from the runtime dependencies. Migrations therefore run before the new version starts, and a failed migration fails the deploy while the running version stays up. | Render's free plan has no pre-deploy command, and running migrations at every start would slow each wake-up after the service sleeps. | Migrations at API start-up; a manual step before each release |
| D42 | Pay totals and rounding | Pay items apply from `effective_from` up to, but not including, `effective_to`, with at most one open item per employee and component (a partial unique index). Totals come from a SQL function `pay_totals_on(date)`, with the `current_pay_totals` view applying it to today, so tests can fix the date. The database returns exact annual totals in minor units; the monthly equivalent is derived from the annual total by the shared helper, rounding half to even, and never by adding rounded monthly amounts. | One rounding rule everywhere, and date-driven tests that do not depend on the clock. PostgreSQL `round` rounds halves away from zero, which would disagree with the helper by one minor unit. | Monthly amounts rounded in SQL; a view fixed to the current date only |
| D43 | Seed data details | The generator is pure TypeScript: Faker instances with a fixed seed and a fixed reference date (1 Sep 2026), so the same data loads on every run and tests can check it without a database. Country counts are exact (largest remainder); employment types, departments, levels and regions are weighted random picks. Each employee keeps the same set of components across pay changes, and earlier pay is worked back from current pay by the raise at each change. The load is one transaction and writes no change log entries, since it is a bulk load and not a user change. Reset truncates the seeded tables and keeps reference data. | Repeatable demos and tests, realistic pay for the dashboard, and a reset that takes seconds instead of deleting 140,000 rows one by one. | Static CSV files; seeding through the API services |
| D44 | Sign-in details | Passwords use `@node-rs/argon2` (Argon2id, OWASP defaults), which ships prebuilt binaries and needs no install script. Sessions are an HS256 JWT from `jose` with the user ID and token version, in an httpOnly, SameSite=Lax cookie for 8 hours, Secure in production. Every request reloads the user, so deactivation or a raised token version ends sessions at once. All `/api` routes need a session except health and auth, so unknown paths answer 401 before 404. Unknown emails are checked against a dummy hash so failures take the same time. Login is limited per email (5 failed attempts in 15 minutes) and per IP (20 in 15 minutes), in memory; the API trusts `X-Forwarded-For` behind Vercel and Render (`TRUST_PROXY`). The five demo HR users share one password from `SEED_HR_PASSWORD`. | Follows D17 and HLD section 7. The per-email limit protects each account even if an IP address is spoofed by calling the API directly. One demo password keeps the setup simple; the README publishes demo logins at release. | `argon2` (needs an install script); a session table; a shared rate limit store such as Redis |
| D45 | Web app foundations | React Router in library mode (routes defined in code, no framework mode). Tailwind CSS with shadcn/ui-style components written in the repository (Button, Input, Label, Card, Alert); Radix packages are added when a component needs them; since step 11 every dropdown uses a styled Radix Select (`@radix-ui/react-select`), with its icons drawn as inline SVG instead of an icon library. Forms use React Hook Form with the shared Zod schemas. The current user is loaded once with TanStack Query; logout marks it signed out and drops every other cached answer. | Matches D5 and D6 without code generators or downloads, and keeps pay data out of memory after sign-out. | React Router framework mode; the shadcn CLI |
| D46 | Reset and invite details | Forgot password answers 202 before looking up the user, then creates the token and sends the email, so neither the answer nor its timing shows whether an account exists. Using a token is one conditional UPDATE, so it works once even for simultaneous requests; a new link of the same purpose ends older unused ones. Setting a password runs in one transaction: use the token, replace the hash, raise the token version and write the change log ("password: hidden to changed"). The Brevo sender calls the HTTP API with `fetch`, passed in for tests; locally a console sender logs the email, and it is refused in production because it logs links. New passwords need at least 12 characters. Limits: 3 reset emails per email and 10 per IP address in 15 minutes; 20 set-password attempts per IP address. | Follows D18 and HLD section 7 without an email SDK, keeps tests off the network, and stops the endpoint being used to flood a mailbox or use up Brevo's 300 emails a day. | The Brevo SDK or SMTP; awaiting the email before answering |
| D47 | Protecting main | A GitHub ruleset on the default branch requires a pull request (no approvals, since a solo author cannot approve their own), the CI check "Lint, typecheck, test and build", and merge commits only; it blocks force pushes and deletion, with no bypass. Squash and rebase merges are turned off for the repository, and merged branches are deleted. | Every change reaches main through a reviewed, green pull request, and each step stays one group of small commits, as section 2.1 of the plan requires. | Branch protection rules (older); requiring branches to be up to date (extra CI runs for no gain here) |
| D48 | User management rules | Endpoints that a role may not use at all answer 403 ("Only global HR users can manage users"), while records outside a user's scope answer 404 (D23). Nobody can deactivate themselves or change their own role. Role and country are checked together against the current values, in a plain function tested without a database. Deactivation raises the token version. Adding a user and creating the invite token share one transaction with the change log; the email is sent after it commits, and a failure is reported (`inviteSent: false`) instead of undoing the user. The change log records email, name, role, country and active status, never password data. | Clear errors for the UI, no way to lock out every global HR user, and a saved user even when the email service is down. | 404 for role-restricted endpoints; sending the email inside the transaction |
| D49 | Exchange rate details | The Frankfurter client (`api.frankfurter.dev/v1`) is passed in, so tests use fixed rates. Refresh inserts one row per currency (USD stored as 1) for the provider's date and ignores dates already stored. The latest rates are the newest on or before today per currency, and their date is the oldest of those, so every rate shown is at least that recent; rates more than 3 days old are marked stale. The scheduled endpoint takes `Authorization: Bearer <secret>`, compared in constant time on SHA-256 digests, needs no session, and is off when no secret is set. The workflow calls Render directly with retries, since a sleeping service can take a minute to wake. Conversion is exact bigint arithmetic on the decimal rates, rounded half to even once. The web toggle is kept in the URL and in local storage; an amount without a rate is shown in local currency rather than wrongly converted. Dates are formatted by hand, since browsers disagree on short month names ("Sep" or "Sept"). | Follows D28 and D29 with no network calls in tests, no repeated or overwritten history, and links that show the same currency to everyone. | Overwriting rates for a date; calling the API through Vercel from the workflow |
| D50 | Employee directory details | One SQL statement joins employees to `pay_totals_on(today)` and the latest rate per currency, with the date from the application clock. Filters are equality matches on indexed columns; search matches part of the full name with the same expression as the trigram index, or the start of the employee code, with LIKE wildcards escaped. Sorting by annual total compares US dollar values in SQL; amounts shown are converted afterwards with the exact shared helper. The employee code breaks ties so pages never repeat or skip rows. The page, the count and the rates are read in parallel. Scope is applied to every query, so a country HR user asking for another country gets an empty list. The web app keeps every filter, the sort and the page in the URL, read with the same schema as the API, and keeps the current page on screen while the next loads. | Fast enough with 10,000 employees (about 90 ms in the database for the heaviest sort) with no stored totals, one conversion rule, and shareable views. | Sorting local amounts across currencies; stored totals on the employee row (HLD 8 fallback) |
| D51 | Employee record details | New employees are always active. In step 12, `GET /api/employees/:id` returns the details; current pay totals and starting pay come with the pay work in step 13. The employee code is trimmed and upper case, uses letters, digits and hyphens, is unique across all countries (the database constraint answers 409, which also covers two requests at the same moment) and cannot be edited, since imports match on it (D20); the country changes only through a move (D35). Job titles and departments are trimmed to single spaces and reuse the spelling already stored in the user's scope, ignoring case; new values are kept as typed. The form suggests the job titles and departments already in use in a list styled like the other dropdowns, and still accepts new values. Regions come from a fixed list of every state, province and territory of the four countries in the shared package. Country fields are checked against the employee's country and logged one by one. Marking inactive takes a date from the hire date up to today (UTC, today by default); making the employee active again clears it. A country HR user adding an employee in another country gets 403, while reading or changing one gets 404 (D23), and change log entries are also read within the user's scope. The inactive confirmation is shown in the page, as on the Users page. | One code per person for spreadsheets; job titles that group together in filters and statistics without changing how people write them (the mitigation in section 4.5 of the design approach); scope applied to every query; no new dependency. | Editable employee codes; title case for every job title; matching spelling across all countries; the browser's own suggestion list (`datalist`); free-text regions; a dialog component for the confirmation |
| D52 | Pay change details | A pay change must be dated after the employee's latest pay change, scheduled ones included, and never before the hire date, so items never overlap; it changes, adds or ends components, and a change that keeps the same amount and frequency is refused. Components must be active and used in the employee's country or in all countries, and amounts must be in the country's currency. The rules are plain functions; the service locks the employee row and writes the change, the ended and new items and the change log in one transaction. Inactive employees' pay cannot change (409). Starting pay is optional in `POST /api/employees` and saved in the same transaction from the hire date with the reason "hire". A move (global HR only, 403 otherwise) cannot be dated in the future, since the country changes at once; it ends every open item, starts the new pay in the new currency, clears the country fields and is logged as "transferred" plus a pay change. Pay changes are logged with each component's old and new amount, and the employee's change log includes them, each entry naming its record type. History lines are worked out from the items that start with a change and those that end on its date. As decided with Vineet: the read-only `GET /api/pay-components` came in step 13 (step 14 adds add, rename and deactivate); `GET /api/employees/:id` returns today's totals as HLD 5 says, alongside `GET /api/employees/:id/pay`; and the employee page converts amounts to US dollars in the browser with the `Money` component from step 10, instead of a `currency` parameter on the pay endpoints. The dialogs use `@radix-ui/react-dialog` (D45). | No overlapping or back-dated items, one set of rules for every way pay changes, and a history that shows exactly what each change did. | Replacing items in place; allowing changes dated before the latest one; converting to US dollars in the API for the employee page |
| D53 | Pay component rules | A component's code uses lower-case letters, digits and underscores (at most 40), is suggested from the name in the form, and is fixed once created, as are its category, country and usual frequency; to change those, HR adds a new component and deactivates the old one. A code must be unique among the components a country can use: a country's component cannot repeat an all-country code, and an all-country component cannot repeat any country's code (409); the unique constraint also covers two requests at the same moment. Country HR users add and change only their own country's components: adding for another country or for all countries answers 403, changing another country's component answers 404 and changing an all-country component answers 403. Components can be renamed, deactivated and reactivated, and every change is written to the change log with the component's country (null for all countries). A deactivated component stays on existing pay items and can still be ended, but cannot be set in new pay changes (D52). The Pay components page is open to both roles. | Import files match one component per code in each country, history stays readable, and mistakes can be undone. | Editable codes; one global list of unique codes; deleting components |
| D54 | Dashboard details | Statistics are SQL over `pay_totals_on(today)`, with the date from the application clock, within the caller's scope and for active employees unless inactive ones are included. Employees without current pay count in headcounts but not in pay statistics. Amounts leave the database as exact integers: sums, minimums and maximums as they are, and quartiles and medians times four (`percentile_cont` only interpolates at quarter points, so these are whole numbers); the API then divides once, rounding half to even, and averages are the sum divided by the count the same way. Each country's figures are worked out in its own currency and converted afterwards with the exact helper from D49. On the all-countries view the summary and department costs add the countries up in US dollars (D28), while per-country figures follow the toggle. Pay by job title is within one country (F7): a global HR user without a country gets 400, and the page gives that section its own country choice, the first country by default. Peer outliers (D32) come from one grouped query of peer medians (taken times two and halved half to even in SQL); groups under five are skipped, and pay is flagged when \|pay - median\| x 100 > median x 20, the same exact rule as `comparePeerPay` in the shared package, which keeps the limit and group size in one value. The list is paged (25), largest relative difference first, with an above or below filter. The measure (total or gross) applies to every figure, peer comparison included. The dashboard replaces the home page at `/` and keeps the exchange rates card; the API and database status list was dropped (`GET /api/health` stays for Render). Charts use Recharts (D6): a box plot per country drawn as a custom bar shape (one chart per country when currencies differ) and bars for departments, each with a table of the same figures; the web bundle grew by about 108 KB gzipped. | Exact figures with one rounding rule, statistics in the database as HLD 8 plans (about 100 ms in the database for the heaviest query on the seed data), and no chart that puts different currencies on one scale. | `percentile_disc` (no interpolation); a peer median query per employee; stored totals (the HLD 8 fallback); charts in plain SVG without Recharts; job titles listed across all countries |

## 2. Decisions from the answered questions

| # | Area | Decision | Reason | Alternatives considered |
|---|---|---|---|---|
| D23 | Roles and country scope (Q1) | Two roles: `global_hr` (all countries) and `country_hr` (one country). The auth middleware builds a scope for each request, and every repository query takes it. A record outside the user's scope returns 404. | Enforced in one place on the server and easy to test for every endpoint. A 404 does not reveal that the record exists. | PostgreSQL row-level security; hiding data only in the UI; a permissions library |
| D24 | User management (Q1) | Global HR users add users, set role and country, and deactivate them. New users receive an invite link to set their password. Users are deactivated, never deleted. Seed data includes one global HR user and one HR user per country. | Covers several HR managers without a sign-up page. | Self sign-up; passwords set by an administrator |
| D25 | Pay model (Q3, Q6) | A catalogue of pay components (`pay_components`: code, name, category, country or all countries, default frequency, active). Each employee has pay items (component, amount, frequency, effective from and to). Changes are grouped into pay changes with a date and reason, so one annual revision can change several components at once. | Matches pay made of several components, lets HR add components, and keeps full history. | One salary column; components stored as JSON on the employee; one row per employee per month |
| D26 | Frequencies (Q3) | A `pay_frequencies` table with periods per year: weekly 52, bi-weekly 26, monthly 12, bi-monthly 6, quarterly 4, bi-quarterly 2, half-yearly 2, yearly 1. "Bi-" means "every two". Annual amount = amount x periods per year. Monthly equivalent = annual amount / 12. | Frequencies are data, so a new one needs no code change, and every conversion follows one rule. | A fixed list in code |
| D27 | Pay measures (Q3, Q9) | Insights use the annual total of all components by default. A switch shows gross pay only (earnings, allowances and bonuses, without employer contributions and benefits). | Total cost answers "how much do we spend"; gross pay answers "how much do people earn". | Base pay only |
| D28 | Currency (Q5) | Pay is stored in the employee's local currency. Conversion to USD happens when reading, using the latest stored rate; the API takes a `currency` parameter. On any view of one country (the dashboard for a country, a filtered directory, an employee record), a toggle switches between USD and that country's currency. On the all-countries dashboard, org-wide totals are always in USD and the per-country figures follow the toggle. | Keeps the amounts HR entered, and lets the same data show both ways. | Converting to USD when saving |
| D29 | Exchange rates (Q5) | Rates from the Frankfurter API (central bank reference rates, no API key), stored per date in PostgreSQL so history is kept. A scheduled GitHub Actions job, which runs on GitHub's servers rather than on our hosting, calls a protected API endpoint once a day, and the API saves the rates. Global HR users can also refresh by hand. Screens show the date of the rates used. Seed data includes starting rates. | Free and reliable, and the scheduled job also works while the free API service sleeps between requests. | Render cron jobs (not on the free plan); Vercel cron (free, once a day, a valid alternative); a timer inside the API (unreliable when the service sleeps); paid rate APIs |
| D30 | Employee fields (Q4) | Common columns for all countries, a region column (state, province or territory), and a small set of country-specific optional fields in a JSON column, validated by a Zod schema per country. No government IDs, bank details, date of birth or gender. | Keeps shared queries simple while allowing country differences. | A table per country; many nullable columns |
| D31 | Inactive employees (Q8) | Status and inactive date on the employee. Inactive employees are left out of lists and insights unless the user includes them. | History and reports stay complete. | Hard delete |
| D32 | Peer comparison (Q9) | Peers share country, job title and employment type. An employee is flagged when their annual total is more than 20% above or below the peer median. Groups with fewer than five people are not flagged. The limits are kept in one configuration value. | Simple to explain and to test, and not skewed by a few very high salaries. | Percentile bands; standard deviation scores |
| D33 | Seed data (Q7) | 6,000 India, 1,500 USA, 1,500 Canada, 1,000 Australia. Employment types: about 80% full-time, 8% part-time, 8% contractor, 4% intern. Components and approximate rates per country from the research notes, one to three pay changes per employee, and some inactive employees. | Realistic data for the dashboard, the filters and the peer comparison. | Uniform random data |
| D34 | Change log | One `change_log` table records every change to employees, pay, pay components and users: what changed, the old and new values, who made the change and when. Services write it in the same transaction as the change. The employee page shows its change log; global HR users can see the log for users. Entries are never edited. | Promotions and department moves keep their history, and there is a record of who changed what, which HR data usually needs. | A history table per entity; database triggers; no log |
| D35 | Moving an employee to another country | Only global HR users can move an employee. In one transaction the country, region and country fields change, all current pay items end, and new pay starts in the new country's currency with the reason "transfer". The move is recorded in the change log. | Pay is stored in local currency, so a move must also restart pay; limiting it to global HR avoids moves between country scopes. | Not allowing moves (a new employee record instead); letting country HR users move employees |
| D36 | Monthly cost | Monthly cost is the monthly equivalent of current pay (annual amount / 12), shown per employee and as totals per country and department. Actual monthly payments are not recorded. | Answers "how much do we spend each month" without becoming payroll, which Q10 excluded. | Recording actual payments each month |

## 3. Answered questions

All eleven clarification questions are answered. See `clarification-questions.md` for each question, the answer and the details decided.
